# Localnet integration tests

The agent tests in `tests/test_agent_localnet.py`,
`tests/test_agent_direct_localnet.py`, `tests/test_agent_rooms_localnet.py`,
`tests/test_agent_policy_localnet.py`, `tests/test_agent_adapters_localnet.py` and
`tests/test_agent_funds_localnet.py` run against a real local
Algorand network: algod, kmd and the indexer. They check what mocks cannot,
such as whether algod accepts transactions signed with the key loaded from the
bot's mnemonic, and whether a message the bot sends is read back by another
account through the indexer.

They are marked `localnet` and skipped when no local network is running, so CI
stays green without one.

Local network only. Every account is generated by the test and funded from the
localnet's own default KMD wallet. The helpers refuse any network whose genesis
id is not a local one (`dockernet-v1`, `devnet-v1`, `sandnet-v1`).

## 1. Start a localnet

With Docker:

```bash
pipx install algokit
algokit localnet start
```

Without Docker (Linux x86_64), from `py/`:

```bash
scripts/native-localnet.sh start   # from py/; first run downloads binaries and takes a few minutes
```

The script pins a SHA-256 for every download (go-algorand, indexer, conduit,
and the PostgreSQL jar plus the archive inside it) and refuses to unpack a file
that does not match; a mismatched file is deleted. The pins come from the
checksums each project publishes with its release.

The script runs the same ports, token and wallet as AlgoKit's localnet: algod on
`127.0.0.1:4001`, kmd on `127.0.0.1:4002` and the indexer on `127.0.0.1:8980`,
each with the token `aaaa…` (64 × `a`). It stores everything under
`~/.cache/algochat-localnet` (override with `ALGOCHAT_LOCALNET_DIR`). Use
`stop`, `status` or `reset` to manage it.

## 2. Run the tests

```bash
cd py
ALGOCHAT_REQUIRE_LOCALNET=1 python -m pytest -m localnet -v
```

`ALGOCHAT_REQUIRE_LOCALNET=1` makes a missing localnet an error instead of a
skip, so a run that should hit the network cannot pass silently.

Optional: with the native script, also cross-check the mnemonic decoder against
go-algorand's own `goal`:

```bash
export PATH="$HOME/.cache/algochat-localnet/node/bin:$PATH"
ALGOCHAT_LOCALNET_ALGOD_DATA="$HOME/.cache/algochat-localnet/net/data" \
  ALGOCHAT_REQUIRE_LOCALNET=1 python -m pytest -m localnet -v
```

### Every language

`tests/test_agent_direct_localnet.py`, `tests/test_agent_rooms_localnet.py`,
`tests/test_agent_policy_localnet.py` and `tests/test_agent_adapters_localnet.py` have people write to the bot with the
TypeScript, Go, Rust, Python and Kotlin implementations, and has every
implementation read the bot's replies. Build their tools first, from the
repository root:

```bash
(cd ts && bun install)
(cd go && go build -o /tmp/algochat-pqcross-go ./cmd/pqcross)
(cd rs && cargo build --bin pqcross)
(cd kt && ./gradlew pqioClasspath)
```

Swift reads the same confirmed notes by running
`swift test --filter AgentDirectLocalnetTests` (and `AgentRoomsLocalnetTests`
for room notes and room chains) on a recorded file, because its
own tool needs macOS 26. The test checks that the Swift test ran rather than
skipped. With `ALGOCHAT_REQUIRE_LOCALNET=1` a missing tool or toolchain fails
the run.

Other endpoints can be set with `ALGOCHAT_LOCALNET_ALGOD_URL`,
`ALGOCHAT_LOCALNET_KMD_URL` and `ALGOCHAT_LOCALNET_INDEXER_URL`.

## What they cover

- The bot account built from the mnemonic in `ALGOCHAT_AGENT_MNEMONIC`, or in an
  owner-only file named by `ALGOCHAT_AGENT_MNEMONIC_FILE`, is the funded
  localnet account, and algod accepts transactions it signs.
- A second account sends the bot an encrypted AlgoChat message; the bot reads it
  through the indexer and replies; the second account reads the reply. Both
  sides only accept encryption keys signed by the account (verified keys).
- Errors (bad checksum, unknown word, too few words, both key sources set, a
  world-readable key file, a short seed, an unfunded bot rejected by algod),
  `repr`s and logs never contain the mnemonic, any three consecutive words of
  it, or the seed in hex, base64 or base32.
- One-to-one replies (`tests/test_agent_direct_localnet.py`): the bot publishes
  its key once, reads a message written by each implementation, answers each
  one itself with a reply that names it, and a restarted bot answers nothing.
  Every implementation, Swift included, opens every note as both parties. A
  second test reads more messages than one indexer page.
- Rooms and channels (`tests/test_agent_rooms_localnet.py`): an owner adds the
  bot to a room and a channel with op 13 and it joins without a request or
  accept; a key handed over by a plain member is ignored. The bot answers a
  room message written by each implementation and a channel message, and a
  restarted bot answers nothing. After a member is removed it answers under the
  new key; it leaves the channel and stays out after a restart; after the owner
  removes it from the room it answers nothing in the room or its channel.
  Every implementation, Swift included, opens every room note and reduces both
  room chains to the same state.
- Reply policy (`tests/test_agent_policy_localnet.py`): in mentions mode the bot
  answers only `@helper` and replies to its own messages, stays within its rate
  limit (also after a restart) and never answers another bot. An admin, then
  the owner, change its mode with op 14 and it follows: in commands mode it
  posts its command list once and answers only its commands and `/help`. A
  one-to-one message from the other bot is not answered. Every
  implementation, Swift included, opens every note and reduces the chain with
  both bots' modes and limits. The test waits out two rate windows, so it takes
  about a minute.
- MCP server, command line and webhook (`tests/test_agent_adapters_localnet.py`):
  the real `algochat-agent` command and its MCP server run as separate
  processes with the mnemonic only in their environment. They publish the
  bot's keys once, answer a person one-to-one and refuse the other bot, list
  every tool, refuse room replies the policy keeps silent and answer a
  mention, and `serve --once` sends a signed webhook on 127.0.0.1 only what
  the policy allows and posts its answers. The command posts the command list
  and leaves the room. Every implementation, Swift included, opens every note
  and reduces the chain, and nothing the processes print carries the key.
